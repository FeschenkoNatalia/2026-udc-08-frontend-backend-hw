# Що AI зробив не так (Task D)

**Інструмент і модель:** Claude Code / Claude Opus 5

**Докази:** `npm test`, реальний Chrome через DevTools Protocol і мутаційне
тестування (прибрати одну умову — чи почервоніє хоч один тест). Кожен запис
має знятий вивід.

## UI

### 1. Форма створення мовчки ковтала відмову сервера

- **Що просив:** Task A — контрол архівування, фільтр, порожній стан.
- **Що видав:** `app/public/app.js`. Агент додав `if (!res.ok)` у кожен
  обробник, який писав сам, і не чіпнув сусідній обробник створення, що був у
  репо до нього. На `400 title is required` інтерфейс очищав поля й мовчав;
  нотатка, додана у вкладці «Архів», не з'являлась ніде.
- **Як помітив:** статичний огляд коду.
- **Як полагодив:** перевірка `res.ok`, окреме повідомлення для 400,
  `aria-invalid` + фокус у поле **лише на 400** (на 500 поле не винне, і
  скрінрідер не має називати його помилковим), повернення до активного
  списку. Закрито трьома тестами в `app/test/ui.test.js`.
- **Гіпотеза:** агент покращує рівно те, на що показали.

### 2. Фокус після видалення стрибав на кнопку іншої дії

- **Що просив:** Task A, клавіатура окремим проходом.
- **Що видав:** `restoreFocus()` шукав тільки `button.archive`, тож після
  видалення фокус переїжджав на «Архівувати» **іншої** нотатки, без видимого
  кільця (взаємодія була мишею).
- **Як помітив:** у Chrome: клік мишею по «Видалити», потім `Space` — замість
  прокрутки заархівувалась сусідня нотатка.
- **Як полагодив:** фокус повертається на контрол **того самого класу** і лише
  коли дію ініціювала клавіатура (`event.detail === 0`). Закрито п'ятьма
  тестами на фокус — клавіатура й миша для обох дій, плюс останній рядок.
- **Гіпотеза:** повернення фокуса агент додав сам — правильний інстинкт, але
  перевірив лише на архівуванні, де клас контрола збігається випадково.

### 3. Доступність «на око»: поля без `<label>`, межі 1.33:1, час на 3 години раніше

- **Що просив:** «Доступність — вимога, а не побажання».
- **Що видав:** нові елементи зроблені добре, і в CSS навіть лишився коментар,
  що контраст тримається в обох темах — але **лише про новий** стан.
  Успадковане не перевірялось: поля без `<label>` (лише `placeholder`, 2.43:1
  у темній темі), межі контролів `#8884` = **1.33:1**, `created_at` сирим
  рядком з SQLite, тобто в UTC.
- **Як помітив:** вимірюванням у браузері, а не оглядом.
- **Як полагодив:** `<label for>`, `border-color` через `color-mix`
  (**4.53:1**), `<time datetime>` з `toLocaleString("uk-UA")`, `<main>`,
  reflow на 320 px. Мітки, межу й `<time>` тримають шість тестів; решту —
  прохід у браузері.
- **Гіпотеза:** агент перевіряє те, що додав, і вважає решту файла даністю.
  Коментар «контраст тримається» — документація, що звучить як перевірка.

## API і база

### 4. Автентифікація без перевірки, що користувач існує → 500 зі стек-трейсом

- **Що просив:** ендпоінт архівування з серверною валідацією (Task B).
- **Що видав:** `Number.isInteger(id) && id > 0` — перевіряє форму рядка, а не
  користувача:

  ```
  POST /api/notes  x-user-id: 999
  -> 500 <pre>SqliteError: FOREIGN KEY constraint failed
        at file:///C:/Users/.../app/src/app.js:98:8 ...
  ```

  `GET` з тим самим заголовком відповідав `200 []`. Окремо: `x-user-id: 0x2`
  **автентифікувався як Тарас** — `Number()` це парсер JS-літералів.
- **Як помітив:** огляд коду; обидва випадки я відтворив на :3080.
- **Як полагодив:** пошук id у `users` → 401; `positiveInt()` приймає лише
  канонічний десятковий запис; JSON-обробник помилок замість HTML Express.
  Тести — на невідомий id, неканонічні записи і на справжній збій (закрита
  база), що доходить до catch-all гілки обробника.
- **Гіпотеза:** «заголовок називає користувача» і «такий користувач існує» —
  різні твердження, і другого в його вході не було.

### 5. Міграція перевіряла лише **ім'я** колонки — і всі нотатки зникали

- **Що просив:** «колонка — міграцією, а не правкою `CREATE TABLE`».
- **Що видав:** `app/src/db.js`. Міграція акуратна (адитивний `ALTER TABLE`,
  guard, `CHECK`, тест), але охоронець — `.some((c) => c.name === "archived")`.
  База з `archived TEXT` від попередньої ітерації проходила мовчки:

  ```
  GET /api/notes            -> 200 []
  GET /api/notes?archived=1 -> 200 []
  ```

  Обидва списки порожні, помилки немає, усі рядки на місці, читання однієї
  нотатки працює — «щасливий шлях» виглядає здоровим.
- **Як помітив:** побудував «дрейфові» бази й прогнав через справжній
  `createApp`.
- **Як полагодив:** перевірка всього контракту колонки — `type`, `notnull`,
  `DEFAULT 0` і `CHECK`; на несподіваній схемі — помилка з поясненням замість
  мовчазного старту. Плюс індекс, сід у транзакції, обмеження довжини. Закрито
  чотирма тестами на «дрейфові» бази (`TEXT`, `INTEGER` без `NOT NULL`, без
  `DEFAULT`, без `CHECK`): старт відмовляє, рядки на місці. Перед
  відмовою `createDb` тепер закриває з'єднання — інакше на Windows файл бази
  лишався заблокованим.
- **Гіпотеза:** агент перевірив міграцію на шляху, який сам і створив. Стан, у
  який база потрапляла через **його ж попередню ітерацію**, у сценарій не
  входив.

## Авторизація

### 6. Засіяна діра: `GET /api/notes/:id` читав нотатку лише за `id`

- **Що просив:** Task C — відтворити витік руками й полагодити.
- **Що видав:** засіяний код, який агент прочитав, написав фічу поруч — і не
  помітив, поки не отримав пряму вказівку шукати:

  ```
  GET /api/notes/3  x-user-id: 1   (Оля просить нотатку Тараса)
  -> 200 {"id":3,"user_id":2,"body":"пароль від сейфа: 1234", ...}
  ```
- **Як помітив:** за вказівкою домашки. **Дев'ять засіяних тестів були зелені
  й до правки** — набір ніколи не ставив це питання.
- **Як полагодив:** `WHERE id = ? AND user_id = ?` у самому запиті, без
  `user_id` у відповіді, 404 замість 403. Тест `will not read someone else's
  note` перевіряє і статус, і вміст тіла; перевірений на червоне.
- **Гіпотеза:** діра виглядає як звичайний CRUD-рядок, а агент не має підстав
  сумніватись у коді, який не писав.

### 7. Найцікавіше: ту саму діру агент повторив у **власній** фічі

- **Що просив:** Task C1 — переконатись, що новий ендпоінт працює з власником,
  а не просто «з id».
- **Що видав:** полагодив засіяний IDOR, написав на нього тест — і тут-таки
  зробив архівний список із тестами, жодного разу не спитавши про власника
  **на новому шляху читання**. Мутація прибирає умову лише в гілці
  `archived=1`:

  ```
  Tests 24 passed (24)          <- набір повністю зелений
  GET /api/notes?archived=1  x-user-id: 1
  -> 200 [{"title":"Приватна нотатка Тараса","body":"пароль від сейфа: 1234"}]
  ```
- **Як помітив:** мутаційним тестуванням — 33 мутанти, 9 вижило.
- **Як полагодив:** два крос-юзерні тести на архів, перевірені на червоне.
  Плюс решта: 401 перевірявся на 1 маршруті з 6, відмови на PATCH і DELETE
  перевіряли лише статус, `SELECT *` у списку проходив непоміченим.
- **Гіпотеза:** набір тестів, написаний тим самим агентом, що й код,
  успадковує його сліпу пляму: питання поставили там, де попросили.

## Власний процес

1. **Мій скрипт перевірки двічі видалив засіяну нотатку** — промахнувся
   `Tab`-ом, потім видалив «першу в списку», не глянувши, яка вона. Помітив,
   бо після прогону дивився в базу. Тепер скрипт не натискає клавішу, поки не
   підтвердить фокус, і створює власну тимчасову нотатку.
2. **`WebFetch` на односторінковий застосунок тихо повертав порожню
   оболонку** — увесь текст у JS-бандлі. Витягнув текст зі скомпільованих
   чанків і далі працював з файлом, а не з адресою.
3. **Два дефекти знайшло людське око, а не автоматичні перевірки:** накладання
   полів форми (`box-sizing: content-box`, інпут 310 px у комірці 292 px) і
   продубльований порожній стан. Їх пропустив навіть прохід, що вимірював
   `getBoundingClientRect()`. Обидва закриті перевірками.

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Умова по власнику — у самому запиті на кожному маршруті**, не перевіркою
  після читання; включно з тими, де цього можна було не робити.
- **Mass assignment заблоковано з обох боків**; `__proto__` не забруднює
  прототип, бо `JSON.parse` робить його власною властивістю.
- **Форма ендпоінта витримала конкурентні й повторені запити** без
  `SQLITE_BUSY` і без «подвійного перекидання» (заміри — у `task-b-api.md`).
- **`will not read someone else's note` — найсильніший тест у наборі:** ловить
  витік **в іншій формі** (404 разом з рядком у тілі).
- **Дев'ять засіяних тестів не зачеплені** — діф лише з додавань.
- **`CHECK` у `ALTER TABLE ADD COLUMN` справді зв'язується** — перевірено
  скриптом, а не припущено.

## Що я перевіряв і воно виявилось чистим

- **Обхід автентифікації написанням шляху:** `/API/notes`, `/api//notes/3`,
  `//api/notes/3`, `/%61pi/notes/3`, `HEAD`, `OPTIONS` — жодне не доходить до
  обробника повз `app.use("/api", currentUser)`.
- **Ізоляція тестів:** `--sequence.shuffle.tests` на двох seed-ах — 89/89.
- **UI не вимагає нічого, чого не вимагає сервер** — асиметрія в безпечний бік.
- Чисті й **XSS**, **обхід статики**, **оракул існування**, **повторений
  `x-user-id`**, **розмір цілі й контраст** — заміри в `docs/evidences/`.

## Висновок

Усі сім записів однієї форми: код робить рівно те, про що просили, у межах,
які показали, — і мовчить про все за цими межами. Порожній архів замість
«схема не та», очищене поле замість «сервер відмовив», зелений набір замість
питання про власника.

Звідси практика. Зелені тести описують те, що спитали, а не те, що правда:
єдиний спосіб дізнатись, чи тест щось перевіряє, — зламати код і подивитись,
чи він почервоніє. Звіт агента теж не доказ, поки його не перевірено. І
власний інструмент помиляється так само, як код —
мій вимірювач контрасту показав хибну помилку, бо Chrome повернув
`color(srgb 0.48 ...)`, а парсер прочитав ці числа як 0–255.

Тому фінальний стан перевірено трьома способами одразу — тестами, браузером і
живими запитами з чужим заголовком: жоден з них окремо доказом не був би.
